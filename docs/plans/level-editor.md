# The level editor with an assistant inside (step 3 after 3.0)

Status: planned; the editor decided 2026-09 to 2026-10, the assistant
decided 2026-11-07, its architecture proposed the same day and not
decided. Third of the six steps after 3.0 (`ROADMAP.md`). Not built; a
third project in `Moon2D.groupproj` is reserved for it.

## Why
Levels 3-10 have to be made of something, and they are built by hand,
not generated. The old route - a whole room from ChatGPT, Claude fitting the
generation onto the grid by hand, slicing, alpha - worked for levels 1-2
and wore thin; it is a route, not a workshop. The editor is the workshop,
and the assistant in it is the apprentice who knows every tool on the
bench.

## The editor (decided)
- **From scratch, not a port.** The 2008 editor wrote `.msv` and a
  six-file legacy format; the game left that for one `levelN.json`.
  Porting the old one would drag a buried format back. The new editor
  writes the JSON directly.
- **WYSIWYG on the game's own renderer.** A separate VCL project in the
  same groupproj, sharing `Levels.Defs`, `Render.Tiles`, `Render.Sprites`
  and the rest of `Core/`; the preview is SDL through
  `SDL_CreateWindowFrom`; F5 launches `Moon2D.exe --level X --screen Y`
  as a separate process. A level is drawn by the engine that plays it.
- **Three phases:** the grid and the tiles first, then the entities, then
  the pain points.
- **The grid comes from the data.** The screen size is a property of the
  level before the editor exists (`wide-frame.md`, step 2 of its order),
  so the editor knows 4:3 and wide from its first day. Proposed, not
  decided: the room size in frames too (1x1 everywhere for now) and a
  canvas that can be larger than the frame - `big-rooms.md` needs both,
  and reopening the format and the editor for them later costs more than
  a field and a scrollbar now.
- **The letter `3` of the collision grid** - bullets pass, the hero does
  not - waits for the editor (`mechanics/pads.md`, the decks).
- Effect properties (colour, intensity and the rest) are to be editable
  here; today they are hand-written JSON.
- The style of the tiles and backdrops of levels 3+ is settled before the
  first screen is drawn in it (`ROADMAP.md`, phase 3, open).

## The assistant (decided 2026-11-07)
Not a generator of levels from scratch. A chat with access to everything
the editor has, helping to build the level by hand: cut an
object into sprites, distribute and place objects, put in lights and
sparks, make the matter map (the transparency / collision grid) for a
piece of art. And the thing the manual route never had: textures and
houses generated by reference right from the editor, fitted onto the
grid there. It is a helper for making this game and then other games on
the same engine.

## The architecture (proposed 2026-11-07, not decided)

**One layer of commands, two clients.** Every action of the editor is a
command with an undo - `PlaceEntity`, `SliceToSprites`, `AddLight`,
`AddSparks`, `PaintMatterMap`, `ImportTexture`, `GenerateByReference` -
and the mouse and the assistant call the same commands. So the assistant
can do nothing the mouse cannot, and anything it does comes back with
Ctrl+Z. The commands are the assistant's tools; the loop "call a tool,
look at the result, call the next" exists in Delphi already (LegacyGrep,
DelphiLoop) and is reused, not reinvented. The assistant sees what the
screen shows: a snapshot of the canvas as a picture plus the level JSON;
without the picture it places lights by touch.

**Generation by reference.** Claude draws no pictures; an image
generator behind an API does, and the manual route becomes a chain of
commands: generate by reference, fit to the 64 px grid, slice into
sprites, build the matter map, place on the level. Beside every
generated asset its prompt, its reference and its parameters are kept -
otherwise the house cannot be redrawn "the same but with a balcony" in
half a year. A set of style references per level goes into every
request, or every new texture comes from a different game.

**An engine for other games.** The editor does not know the Moon2D
entities by name: a catalogue of entities (what it is, which fields it
has, how the editor draws it) is read from data. The engine itself is
NOT lifted out of Moon2D now: lift it when the second game really
starts and shows what the two have in common. Lifting it now means
guessing, and guessing is expensive in this project.

**The order:** 3a - the editor on the command layer with undo, no
assistant; 3b - the assistant chat over the commands; 3c - image
generation and the chain reference - grid - sprites - matter.

## Traps
- The assistant before the command layer: it writes the JSON directly,
  past the checks of `Levels.Defs` (`ELevelError`), and the loader refuses
  the levels it made. The command layer validates once, for both clients.
- An image API has a price per picture; the editor needs a running count
  of what was spent, or an evening of picking a texture for one house
  costs more than expected.
- A generator does not redraw the same picture twice - it draws something
  similar (seen on ChatGPT, 2026-11-01); no step of the chain may depend
  on two generations matching.
